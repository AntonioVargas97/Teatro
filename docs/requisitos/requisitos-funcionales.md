# Especificación de Requerimientos Funcionales - Plataforma de Boletaje y Arrendamiento del Teatro de la Ciudad de Coatzacoalcos

## Módulo 1: Configuración Administrativa y Catálogos Base
| ID | Descripción | Tipo |
| :--- | :--- | :--- |
| RF-01 | El Administrador debe poder actualizar la tarifa base de un turno de arrendamiento, ingresando el identificador del turno (Matutino, Vespertino o Día Completo) con el nuevo importe neto en MXN, para aplicar el costo vigente únicamente a cotizaciones futuras preservando el snapshot previo. | Usuario |
| RF-02 | El Administrador debe poder actualizar el bloque horario de un turno de arrendamiento, ingresando el identificador del turno con la hora de inicio y la hora de fin bajo America/Mexico_City, para fijar los intervalos oficiales de ocupación en futuras solicitudes. | Usuario |
| RF-03 | El Administrador debe poder registrar un servicio extra en el catálogo, ingresando nombre, tipo de concepto (extra o infraestructura escénica), unidad de cobro (POR_EVENTO, POR_DIA, POR_TURNO o POR_UNIDAD) con el precio base neto en MXN, para habilitarlo en el cotizador digital. | Usuario |
| RF-04 | El Administrador debe poder actualizar el precio base de un servicio extra del catálogo, ingresando el identificador del concepto con el nuevo importe neto en MXN, para reflejar la tarifa actualizada solo en cotizaciones nuevas. | Usuario |
| RF-05 | El Administrador debe poder cambiar la disponibilidad de un servicio extra del catálogo, ingresando el identificador del concepto con el estado activo o inactivo, para controlar si puede seleccionarse en nuevas solicitudes de arrendamiento. | Usuario |
| RF-06 | El Administrador debe poder actualizar los parámetros operativos de compra en línea, ingresando los minutos de apartado temporal (10 por defecto), los minutos de gracia por pago en proceso (5 por defecto) el margen de cierre web por función (30 por defecto), el margen de cierre de taquilla física por función (0 por defecto) o el límite máximo de boletos por cuenta/operación (10 por defecto, editable con valor ≥ 1, aplicable estrictamente a nuevas operaciones hacia adelante), para ajustar los parámetros de futuras operaciones. | Usuario |
| RF-07 | El Administrador debe poder actualizar el margen de cierre de taquilla física, ingresando los minutos previos al inicio de la función (0 por defecto), para definir el límite de venta presencial de futuras funciones. | Usuario |
| RF-08 | El Administrador debe poder actualizar los parámetros operativos de cotizaciones, ingresando las horas de pre-reserva (48), horas de vigencia de propuesta (48), horas de revisión extemporánea (72), días límite de publicación (15), días de frecuencia de recordatorios (7), corte de saldo D-21 (21), margen 50/50 (9 con umbral mayor al corte), porcentaje de retención (50%), días mínimos de reprogramación (21), días hábiles de SLA de respuesta (3) o días hábiles de alerta de atraso (5), para aplicar las reglas actualizadas solo a futuras operaciones. | Usuario |

## Módulo 4: Cotización y Arrendamiento del Teatro
| ID | Descripción | Tipo |
| :--- | :--- | :--- |
| RF-24 | El Sistema debe poder calcular un subtotal estimado informativo en MXN neto para una cotización, tomando las tarifas vigentes por turno, los extras elegidos según su unidad de cobro con la exención de cargo extra para bloques exclusivos de montaje o ensayos en multi-día, para mostrar un desglose referencial al Solicitante. | Sistema |
| RF-25 | El Usuario estándar debe poder enviar una solicitud de cotización de arrendamiento, ingresando nombre completo del destinatario, teléfono, correo electrónico, nombre del evento, modalidad (Comercial, Público o Privado), fecha estimada, turno (Matutino, Vespertino o Día Completo), indicador multi-día con días/horarios específicos, asistentes estimados (<= 1,730), servicios extra opcionales, para crear la solicitud en estado EN_REVISION sin bloquear agenda. | Usuario |
| RF-26 | El Usuario estándar debe poder consultar el detalle de una cotización propia, seleccionando la solicitud en su panel de seguimiento, para revisar su estado actual, versiones de monto oficial, avisos de medios de pago o propuestas alternativas. | Usuario |
| RF-27 | El Sistema debe poder marcar como atrasadas las solicitudes pendientes fuera del umbral SLA, comparando la fecha de creación con 5 días hábiles (lunes a viernes bajo America/Mexico_City) o la cercanía a la fecha estimada, para resaltar alertas prioritarias en el panel del Administrador. | Sistema |
| RF-28 | El Sistema debe poder expirar automáticamente una cotización cuya fecha estimada ya transcurrió sin aprobación, evaluando la fecha actual bajo America/Mexico_City, para cambiar la solicitud al estado EXPIRADA_POR_FECHA sin bloquear agenda. | Sistema |
| RF-29 | El Administrador debe poder registrar una versión de monto oficial en una cotización, ingresando el identificador de la cotización, el importe neto en MXN con una nota opcional visible para el Solicitante, para conservar un historial numerado e inmutable de ajustes tarifarios. | Usuario |
| RF-30 | El Administrador debe poder aprobar una solicitud de cotización, ingresando el identificador de la cotización, la versión de monto oficial vigente con el aforo acordado, para fijar el snapshot de pago (50/50 si faltan > 30 días naturales con corte D-21 23:59:59, o 100% si faltan <= 30 días) activando el bloqueo PRE_RESERVADO por 48 horas naturales. | Usuario |
| RF-31 | El Sistema debe poder calcular el anticipo exacto junto con el saldo restante bajo esquema 50/50, aplicando redondeo ROUND_HALF_UP a dos decimales sobre la mitad del monto oficial con resta exacta para el saldo, para evitar diferencias de centavos en montos impares. | Sistema |
| RF-32 | El Administrador debe poder rechazar una solicitud de cotización, ingresando el identificador de la cotización con el motivo del rechazo, para cambiar la solicitud a estado RECHAZADA liberando cualquier retención previa en agenda. | Usuario |
| RF-33 | El Administrador debe poder enviar una propuesta de fechas alternativas, ingresando el identificador de la cotización, de 1 a 3 opciones de fecha/turno libres no traslapadas entre sí con un motivo opcional visible para el Solicitante, para retener todas las opciones en estado PROPUESTA_RETENIDA por 48 horas naturales. | Usuario |
| RF-34 | El Usuario estándar debe poder aceptar una fecha de la propuesta alternativa, ingresando el identificador de su cotización con el identificador de la opción elegida dentro de las 48 horas, para liberar inmediatamente las opciones descartadas manteniendo retenida la elegida hasta la confirmación del Administrador. | Usuario |
| RF-35 | El Usuario estándar debe poder rechazar una propuesta de fechas alternativas, ingresando el identificador de su cotización, para cambiar la propuesta a estado PROPUESTA_EXPIRADA liberando todas las fechas retenidas. | Usuario |
| RF-36 | El Sistema debe poder expirar automáticamente una propuesta de fechas alternativas vencida, evaluando el plazo de 48 horas naturales bajo America/Mexico_City sin respuesta del Solicitante, para pasar la propuesta a PROPUESTA_EXPIRADA liberando todos los bloques retenidos. | Sistema |
| RF-37 | El Usuario estándar debe poder pagar con tarjeta en línea una cuota pendiente de su arrendamiento, ingresando el identificador de su cotización, la cuota correspondiente (anticipo 50%, saldo 50% o liquidación 100%) con los datos de tarjeta mediante Stripe, para acreditar el pago dentro de la ventana vigente. | Usuario |
| RF-38 | El Usuario estándar debe poder generar una ficha de pago con línea de captura (SPEI o efectivo) para su arrendamiento, ingresando el identificador de su cotización, la cuota correspondiente con el medio permitido, para obtener la referencia bancaria respetando las 48 horas de pre-reserva, el margen de 48 horas previas al corte D-21 junto con el tope de efectivo Stripe. | Usuario |
| RF-39 | El Sistema debe poder formalizar un arrendamiento tras recibir la confirmación idempotente del pago inicial vía Stripe dentro de las 48 horas, validando el identificador único del evento de webhook, para pasar el bloqueo de agenda a CONFIRMADO. | Sistema |
| RF-40 | El Sistema debe poder expirar automáticamente una pre-reserva sin pago acreditado, detectando el vencimiento de las 48 horas naturales de PRE_RESERVADO bajo America/Mexico_City, para invalidar la cotización liberando la fecha en agenda. | Sistema |
| RF-41 | El Sistema debe poder colocar en revisión un pago tardío de arrendamiento cuando la fecha sigue libre, recibiendo la confirmación de Stripe después de vencer las 48 horas tras comprobar disponibilidad en agenda, para pasar la cotización a PAGO_EXTEMPORANEO_EN_REVISION con un plazo máximo de 72 horas naturales para el Administrador. | Sistema |
| RF-42 | El Administrador debe poder resolver una cotización en estado PAGO_EXTEMPORANEO_EN_REVISION, ingresando el identificador de la cotización, la decisión (aceptar o rechazar) con el motivo, para consolidar la reserva en CONFIRMADO o tramitar la devolución íntegra del 100% según el medio de pago. | Usuario |
| RF-43 | El Sistema debe poder procesar la devolución íntegra del 100% de un pago tardío de arrendamiento cuando la fecha ya está ocupada o posterior al incumplimiento de D-21, recibiendo la confirmación extemporánea de Stripe, para ejecutar un reembolso técnico automático vía Stripe API si provino de tarjeta o registrar REEMBOLSO_BANCARIO_PENDIENTE con alerta prioritaria al Administrador si provino de ficha SPEI/efectivo. | Sistema |
| RF-44 | El Sistema debe poder acreditar el pago del saldo restante del 50% antes del corte D-21 a las 23:59:59, procesando el evento idempotente de Stripe para la cuota final, para marcar el arrendamiento como liquidado al 100%. | Sistema |
| RF-45 | El Usuario estándar debe poder solicitar la cancelación de su arrendamiento, ingresando el identificador de su cotización con el motivo estructurado desde su panel de seguimiento, para turnar la petición a revisión del Administrador sin chat interno. | Usuario |
| RF-46 | El Administrador debe poder registrar la cancelación de un arrendamiento por iniciativa del arrendatario o por incumplimiento de saldo en D-21, ingresando el identificador de la cotización con el motivo, para cambiar el estado a CANCELADO_POR_ARRENDATARIO aplicando la regla de retención según el umbral de 21 días naturales sin borrar historial. | Usuario |
| RF-47 | El Administrador debe poder cancelar un arrendamiento por decisión del Teatro o fuerza mayor, ingresando el identificador de la cotización con el motivo, para cambiar el estado a CANCELADO_POR_TEATRO habilitando la elección del Solicitante. | Usuario |
| RF-48 | El Usuario estándar debe poder registrar su elección ante una cancelación en estado CANCELADO_POR_TEATRO, ingresando el identificador de su cotización con la opción elegida (reembolso externo del 100% o reprogramación sin costo), para formalizar la resolución en su seguimiento. | Usuario |
| RF-49 | El Usuario estándar debe poder solicitar la reprogramación de su arrendamiento, ingresando el identificador de su cotización, las nuevas fechas/turnos propuestos con el motivo, para tramitar el cambio gratuito único sujeto a 21 días naturales mínimos de anticipación. | Usuario |
| RF-50 | El Administrador debe poder ejecutar la reprogramación atómica de un arrendamiento, ingresando el identificador de la cotización, los nuevos bloques disponibles en agenda con el motivo, para reservar el nuevo horario liberando simultáneamente el anterior recalculando el corte D-21 junto con la fecha límite de publicación (exigiendo liquidar el 100% si la nueva fecha queda a menos de 21 días con saldo pendiente). | Usuario |
